# Lean 4 Web アプリケーションにおける WebSocket 利用のリスク・リターン / コスト・リターン分析

所属: [Web ApplicationのStudy](./README.md)。アプリ実装から得た分析と、
[Std拡張WebSocket開発](../std-websocket/README.md)へ派生した理由を残す経緯資料。
付録の候補比較は、派生側の現在の採用方針・保証を示すものではない。

2026-11-02 作成。本リポジトリで実装した三つのチャット
（`/chat/` libwebsockets、`/chat-ws/` ws-lean、`/chat-sse/` SSE）と
リアルタイム Pong（`/pong/`）の実装経験に基づく。個別の技術選定の経緯と
プロトコル仕様は [websocket-chat.md](websocket-chat.md) を参照。

## 1. 前提となる構造的制約

分析の出発点は、WebSocket フレーム処理そのものではなく
**HTTP 接続の所有権移譲**が最大の難所だったという知見である。

固定された Lean 4.35.0 の `Std.Http.Server.Handler` は
「リクエストを受けて Response を返す」抽象であり、接続ソケットを
Handler に公開しない。101 Switching Protocols を通常の Response として
返しても、以後の読み書きを WebSocket に切り替える契約にはならない。
統合には、先読みバイトの引き継ぎ、読み書き権限の一方的な移譲、
接続タスク・キャンセル・後始末の一元管理が必要で、Handler の結果型から
接続ループまでにまたがる設計変更になる。

この制約から、本リポジトリの両 WebSocket 実装は **HTTP とは別の
loopback リスナー**を同一プロセス内に立てる構成を取った。その帰結として:

- ポート発見用のメタデータエンドポイント（`/chat/endpoint`、
  `/chat-ws/endpoint`）が必要になった。
- 開発 watcher（`tools/dev.py`）が `/chat/socket` 等のハンドシェイクと
  バイト列を別ポートへトンネルする実装を持つことになった。
- リモートからのポート転送では HTTP と WebSocket の二つのポートが必要になる。

つまり「Lean で WebSocket を使えるか」の答えは「使える」だが、
**同一ポート統合を諦めるコストが構成全体（発見・プロキシ・運用）に波及する**。

## 2. 実装から得られた主な知見

### 2.1 libwebsockets + C ブリッジ（`/chat/`、`/pong/`）

- プロトコル処理（Upgrade、マスク、断片化、UTF-8、Ping/Pong、Close）を
  成熟した C ライブラリーに委譲でき、Lean 側は JSON 検証と配信イベント
  生成（`LeanWebStudy.Chat.response`）に集中できた。
- C ブリッジは `native/chat.c` の約 360 行。既存 SQLite FFI と同じ
  ビルド方式（`-lwebsockets`）に乗り、Lake の Git 依存は増えない。
- Lean の純粋関数を C のコールバックから呼ぶ構成は安定して動作した。
  検証ロジックが Lean 側にあるため、チャットと Pong で検証器を
  差し替えるだけで二つのアプリケーションを同じリスナーに同居できた。
- 代償はシステム開発ライブラリー依存（`libwebsockets-dev`）、
  C のキュー・ライフサイクル管理、そして Lean の型システムの外にある
  メモリー安全性をレビューとテストで担保する負担である。

### 2.2 ws-lean（`/chat-ws/`）

- Lean 製 sans-I/O 層（`Ws.Message`、`Ws.Transport.Http1`、
  `Ws.Transport.Plain`）に import を限定すると、無改変の upstream が
  Lean 4.35.0 でビルドできた。ただし集約ターゲット `lake build Ws` は
  `Tls.Handshake` と `Http2.Frame` の証明エラーで失敗する。
  **「必要なサブセットだけ固定して使う」運用が成立する**ことと、
  **ライブラリー全体の互換性は保証されない**ことの両方が知見である。
- 高レベル API（`Ws.Connection` の送受信）は通常ワーカーの IO
  ポーリングを使い、2 CPU の Dev Container では履歴送信が停止した。
  プレリリースの高レベル API を低リソース環境でそのまま使うのは危険で、
  sans-I/O 層 + 自前の `Std.Async` ランタイムという分担に落ち着いた。
- その結果、接続上限（64）、接続ごとの有界キュー（64）、Ping/Pong 送出、
  無応答切断（30 秒）、Upgrade 期限（10 秒）、書き込み期限（5 秒）、
  遅いクライアントの 1008 切断といった**運用品質の機構はすべて
  アプリ側で実装・検証する必要があった**（`LeanWebStudy/WsChat.lean`、
  約 260 行）。フレーム処理より、この周辺機構の方が設計・テスト量が多い。
- 見返りとして、C ブリッジ不要・追加システム依存なし・ロジックが
  Lean の型と `Std.Mutex`/`Std.CloseableChannel` で表現でき、
  履歴登録と配信順序の整合性を mutex 内の順序付けとして明示できた。

### 2.3 SSE + POST（`/chat-sse/`）

- サーバー→ブラウザーの一方向配信で足りる用途なら、HTTP Upgrade を
  完全に回避できる。`EventSource` の自動再接続・Last-Event-ID 相当の
  連番管理をブラウザーが肩代わりし、実装は約 160 行で済んだ。
- 必要だったのは Lithe レスポンスを Std のストリーミング Body へ変換する
  アダプターのみで、別リスナーもポート発見も不要。既存の HTTP
  インフラ（Origin 検証、プレビュー転送）をそのまま使える。
- 制約は投稿が別 HTTP 要求になること（双方向ではない）と、
  接続ごとのキュー・接続数上限を同様に自前で持つ必要があること。

### 2.4 テスト・開発体験

- 実サーバーに対する Python 標準ライブラリーのみのテスト
  （`tests/test_chat.py`、約 620 行）で、配信・断片化・Ping/Pong・
  Close・Origin 拒否・接続上限・トンネルまで検証した。
  **プロトコル層を外部に委譲しても、結合点（上限、期限、順序）の
  テストコストは消えない**。タイマー検証は実時間で約 30 秒かかり、
  watcher 統合テストは 10 分を超え得る。
- 開発プレビューのトンネルは WebSocket をフレーム解釈なしのバイト転送で
  実現でき、プロキシ実装は比較的安価だった。一方で Host/Origin 検証を
  プレビューとバックエンドの二箇所で行う必要が生じた。

## 3. リスク・リターン分析

| 観点 | libwebsockets + C | ws-lean sans-I/O | SSE + POST |
| --- | --- | --- | --- |
| リターン | 成熟したプロトコル処理、双方向低遅延、複数アプリ同居実績 | 全スタック Lean、型による状態管理、依存はソース固定のみ | 最小コストの準リアルタイム、ブラウザー再接続 |
| 技術リスク | C FFI のメモリー・ライフサイクル欠陥が Lean の型の外にある | プレリリース API の変更、toolchain 更新で証明が壊れる、低リソースでの実行時挙動 | 双方向要件が出た時点で作り直し |
| 供給リスク | 低（広く使われる C ライブラリー、ディストリ更新に追随） | 中〜高（コミット固定でしか再現できず、全体ビルドは失敗する） | 低（Std のみ） |
| セキュリティ面 | ライブラリー側の制限（FD・ヘッダー）を利用できる | 制限をすべて自前実装するため見落としリスクを負う | HTTP と同じ防御面を再利用 |
| 運用リスク | 別ポート運用、トンネル・ポート発見が単一障害点になる | 同左 | なし（同一ポート） |

リスクの質が方式ごとに異なる点が重要である。libwebsockets は
**実行時の安全性リスクを C 側に**、ws-lean は**供給・互換性リスクを
依存の固定に**、SSE は**要件変化リスクを設計に**置いている。
どれもローカル学習用途では顕在化しなかったが、公開運用では
TLS・認証・永続化・複数プロセス配信が未実装である点が共通の上限になる。

## 4. コスト・リターン分析

初期コスト（概算の実装規模）:

| 方式 | 専用コード | 追加依存 | 周辺コスト |
| --- | --- | --- | --- |
| libwebsockets | C 約 360 行 + Lean FFI 宣言約 50 行 | システムライブラリー 1 つ | 別リスナー、ポート発見、トンネル対応 |
| ws-lean | Lean 約 260 行 | Git 依存 3 つ（コミット固定） | 同上 + 上限・期限・キューの設計と検証 |
| SSE | Lean 約 160 行 | なし | ストリーミング Body アダプターのみ |

維持コストはこの順位と一致しない。libwebsockets はディストリの更新に
追随するだけで済む一方、C ブリッジの変更には FFI の知識が要る。
ws-lean はコードが少なく見えるが、**toolchain 更新のたびに
`lake update ws-lean` → サブセットビルド → 実通信テストの再実行**という
検証サイクルがマニフェスト固定とセットで必要になる。SSE は維持コストが
最小で、双方向が不要な限りリターン密度（機能/行数）が最も高い。

共通の隠れコストとして、別ポート構成が課す「発見・トンネル・二重 Origin
検証」は方式を問わず WebSocket を選んだ時点で発生する。これは
`Std.Http.Server` に Upgrade API がないことに起因する固定費であり、
アプリを増やしてもほぼ増えない（Pong はチャットのリスナーに同居できた）が、
ゼロにもできない。

## 5. 選定指針

1. 配信が一方向で足りるなら SSE。コスト最小で既存 HTTP 防御面を再利用できる。
2. 双方向・低遅延が必要で、システムライブラリー依存を許容できるなら
   libwebsockets + C ブリッジ。運用品質の多くをライブラリーに委譲できる。
3. 全スタックを Lean に保ちたい、または C FFI を避けたい場合は
   ws-lean の sans-I/O 層 + 自前ランタイム。ただし上限・期限・
   バックプレッシャーの設計と、依存固定の検証サイクルを引き受けること。
4. いずれの場合も同一ポート統合は現状不可能であり、ポート発見と
   プロキシの固定費を見込むこと。

## 6. トレードオフを改善する実装の提案

### 6.1 エコシステム側（効果が最も大きい順）

1. **`Std.Http.Server` の Upgrade / 接続移譲 API。**
   Handler の結果型に「101 送信後にソケットと先読みバッファーを
   呼び出し側へ移譲する」応答種別を追加し、移譲後は HTTP 側の
   接続管理（読み書き・タイムアウト・後始末）が手を引く契約を定める。
   これが実現すると、別リスナー・ポート発見・開発トンネル・二重
   Origin 検証・二ポート転送という本レポートの固定費が一括で消え、
   libwebsockets 依存も不要になる。三方式のコスト差が「プロトコル層を
   どこに置くか」だけの比較に縮退する。
   API の形は新規に発明する必要はない。他言語の HTTP サーバーが
   同じ問題を解いた実績あるデザインの調査と、Lean に向く形の考察を
   [付録 A](#付録-a-接続移譲-api-の先行デザイン調査) にまとめた。
2. **ws-lean の安定化とモジュール分割。**
   HTTP/1.1 + WebSocket コアを TLS/HTTP/2 の証明群から分離した
   安定ターゲットとしてタグ付きリリースし、安定版 toolchain での
   Lake ビルドを CI 対象にする。加えて高レベル `Ws.Connection` の
   IO ポーリングを `Std.Async` のイベント駆動へ置き換えれば、
   本リポジトリが自前実装した接続ランタイム約 260 行の大半を
   ライブラリーへ還元できる。
3. **接続運用プリミティブの標準化。**
   有界キュー + 書き込み期限 + 超過時 Close という「遅いクライアント
   対策」の定型を、`Std.CloseableChannel` 周辺の汎用コンビネーターか
   ws-lean のサーバー層として提供する。どの方式でも自前実装していた
   部分であり、見落としによるメモリー増大リスクを型で封じられる。
4. **検証済みプロトコル層という Lean ならではの差別化。**
   UTF-8 検証・フレーム長・マスク処理など RFC 6455 の不変条件を
   定理として持つプロトコル層と、Autobahn 相当の適合テストスイートが
   揃えば、「C に委譲して安全性をテストで担保する」現状の構図を
   「Lean で証明して委譲を不要にする」構図へ逆転できる。

### 6.2 本リポジトリ側（エコシステムを待たずにできること）

- 三実装の共通部分（接続上限、履歴リング、Origin 検証、有界配信）を
  ひとつの Lean モジュールへ抽出し、プロトコル層を差し替え可能にする。
  方式間の乗り換えコストが下がり、6.1 の API が登場した際の移行も
  差分が小さくなる。
- ws-lean の検証サイクル（サブセットビルド + 実通信テスト）を
  CI 化し、固定コミット更新の判断を機械化する。供給リスクを
  「更新時に気付く」から「常時監視」へ変える。
- 公開運用を視野に入れる段階になったら、TLS 終端・認証・永続化・
  複数プロセス配信を別レイヤー（リバースプロキシ + ジョブ/ブローカー）
  として設計し、本体の WebSocket 実装を肥大させない。

## 7. 結論

Lean 4 での WebSocket は「プロトコル処理をどこに置くか」より
「HTTP サーバーとの接続境界をどう越えるか」が支配的なコスト要因だった。
現状の最適解は用途依存で、一方向なら SSE、双方向なら libwebsockets 委譲が
コスト・リターン比で優位、純 Lean 構成は供給リスクと周辺機構の自前実装を
許容できる場合の選択肢である。`Std.Http.Server` に接続移譲 API が入れば
この比較の前提が崩れ、固定費の大半が消えるため、エコシステムへの
最重要の要望はその一点に集約される。

## 付録 A: 接続移譲 API の先行デザイン調査

2026-11-02 追記。提案 6.1-1 の API は新規発明する必要がなく、他言語の
HTTP サーバーが同じ問題（短命な request/response 抽象から長命な双方向
セッションへの境界）を長年かけて解いてきた。実績あるデザインは
次の四系統に分類でき、それぞれ第 1 節で挙げた三つの整合性要件
（先読みバイト、101 前後の所有権、後始末の一元化）への答え方が異なる。

### A.1 生ソケット奪取型（escape hatch / hijack）

サーバーが「以後この接続に関与しない」と宣言し、生の接続を渡す。

- **Go `net/http` の `http.Hijacker`**:
  `Hijack() (net.Conn, *bufio.ReadWriter, error)`。先読みバイトは
  `bufio.Reader` ごと渡る。以後のクローズ・タイムアウト・101 送信は
  すべて呼び出し側の責任で、gorilla/websocket 等がその上に実装される。
- **Node.js の `server.on('upgrade', (req, socket, head) => …)`**:
  先読みバイトが `head`（Buffer）という**明示的な引数**になっている。
  Upgrade 要求は通常のリクエスト処理に届かず、イベントで経路が分岐する。
- **Java Servlet 3.1 の `HttpServletRequest.upgrade(...)`**:
  コンテナが `WebConnection` をハンドラーへ渡す。

利点は最大の柔軟性（WebSocket 以外のプロトコルにも使える）。
代償は、101 送信・クローズ・タイムアウトという契約が型に現れず
呼び出し側へ漏れることで、Go では `w.(http.Hijacker)` の型アサーションが
HTTP/2 接続で実行時に失敗するという「静的に見えない失敗」が知られている。

### A.2 型付き移譲・future 型

101 の送信をライブラリーが行い、**送信完了後に**双方向ストリームが
解決される。時系列の制約を型（future）で表現する。

- **Rust hyper の `hyper::upgrade::on(req)`**: `OnUpgrade` future を
  取得し、ハンドラーは 101 Response を通常どおり返す。hyper が 101 を
  書き終えてから future が `Upgraded`（AsyncRead/AsyncWrite。先読み
  バイトは内部バッファーとして保持）に解決される。
- **axum の `WebSocketUpgrade`**: その上のエルゴノミック層。
  `ws.on_upgrade(|socket| async { … })` を Response として返すだけで、
  利用側の認知コストは四系統中もっとも低い部類。
- **ASP.NET Core**: `HttpContext.WebSockets.AcceptWebSocketAsync()`、
  下層は `IHttpUpgradeFeature.UpgradeAsync() → Stream`。ハンドラーが
  完了するまでサーバーが接続を生かすというライフサイクル規約を持つ。

「101 の前後で両者が同じソケットを読まない」という要件が
future の解決時点として構造化され、呼び出し側が順序を誤れない。

### A.3 ハンドラー戻り値によるプロトコル切替(sum type)

第 1 節の「Upgrade を通常応答と区別して表現」に最も近い系統。

- **Haskell Warp の `responseRaw`**: WAI の `Response` の
  **コンストラクタの一種**として
  `responseRaw :: (IO ByteString -> (ByteString -> IO ()) -> IO ()) -> Response -> Response`
  を持つ。raw 非対応サーバー向けのフォールバック Response を同時に
  要求する点も含め、`Handler : Request → IO Response` という抽象を
  **壊さずに**移譲を追加した実例。wai-websockets の `websocketsOr` が
  この上にある。
- **Erlang Cowboy**: ハンドラーの `init/2` が
  `{cowboy_websocket, Req, State}` を返すと、サーバーが接続の
  プロトコルハンドラーを交換する。接続（プロセス）の所有権が終始
  サーバー側に残るため、後始末の二重管理が構造的に起きない。

### A.4 移譲しない(サーバー保持 + 型付きイベント)

- **ASGI 仕様（Python）**: `scope["type"] == "websocket"` の接続に
  対し、アプリは `connect / accept / receive / send / close` という
  イベント列だけを扱い、ソケット移譲が**仕様から存在しない**。
  WSGI が移譲を表現できず WebSocket に対応できなかった反省から
  生まれた、本レポートと同じ問題への仕様レベルの解である。
  wsproto のような sans-I/O 実装と相性が良い。

三つの整合性要件がすべてサーバー実装側に閉じる代わりに、
WebSocket の知識（accept、フレーム種別）が HTTP サーバーの仕様に
入り込む。汎用の接続移譲（WebSocket 以外）には使えない。

### A.5 Lean（`Std.Http.Server`）への適用案

| 要件 | A.1 hijack | A.2 future | A.3 sum type | A.4 イベント |
| --- | --- | --- | --- | --- |
| 先読みバイト | 引数で渡す（忘れると壊れる） | ストリームに内包 | ストリームに内包 | 問題自体が消える |
| 101 前後の所有権 | 呼び出し側任せ | future の解決時点で構造化 | サーバーが切替を実施 | サーバーが保持 |
| 後始末の一元化 | 呼び出し側へ全部漏れる | 規約 + 型で分担 | サーバー側に残せる | サーバー側に閉じる |
| 認知コスト | 高 | 低（上位層があれば最低） | 低 | 低 |
| 汎用性（非 WebSocket） | 最高 | 高 | 高 | なし |

Lean に流用するなら **A.3（Warp `responseRaw`）を骨格に、A.2（hyper）の
時系列規約を組み合わせる**形が最も既存抽象と噛み合う。すなわち:

1. `Handler` の結果型（Response 相当）に、純粋関数型の先例どおり
   「ステータス行とヘッダー + 移譲後の双方向ストリームを受け取る
   継続」を持つコンストラクタを追加する（Warp 型）。
2. 101 の送信はサーバーが行い、送信完了後にのみ継続を起動する。
   継続が受け取るストリームは先読みバイトを内包する（hyper 型）。
   これで「101 前後で両者が同じソケットを読まない」要件が
   呼び出し側の注意ではなく API の構造で保証される。
3. 継続の完了・例外をサーバーの接続後始末に接続し、所有権を
   サーバー側に残す（Cowboy 型）。hijack 型のように後始末を
   呼び出し側へ漏らさない。

A.4（ASGI 型）は `Std.Http.Server` に WebSocket の知識を持たせる案として
検討価値があるが、HTTP サーバーの責務が増え、WebSocket 以外の
プロトコル移行（例: HTTP/2 cleartext upgrade）に再利用できない。
汎用の移譲プリミティブ（1〜3）を Std に置き、その上に ws-lean が
axum 相当のエルゴノミック層を提供する二段構えが、実装の楽さ・
認知コスト・問題発生時の切り分けやすさの三点で最も釣り合いが良い。

### A.6 補強: 抽象漏れの帰結と、ストリーミング応答との寿命管理の統一

2026-11-02 の議論からの追記。A.5 の適用案を二つの観点から補強する。

**hijack の害は低水準さ自体ではなく、内部状態を契約にすること。**
Go の `Hijack()` が返す `*bufio.ReadWriter` は、HTTP パーサーの
バッファリング戦略という内部実装の露出である。この抽象漏れの帰結が
最も鮮明に現れるのが HTTP/2 で、リクエストは多重化ストリームであり
「奪える単一ソケット」が存在しないため、Hijacker は実装不可能になり、
実行時の型アサーション失敗として観測される。内部が透ける API は
内部が変わった瞬間に壊れ、しかもそれを型が隠す。試金石は RFC 8441
（HTTP/2 上の WebSocket、extended CONNECT）で、hyper の `Upgraded` は
「抽象的な双方向バイトストリーム」としか約束しないため、下が
HTTP/1.1 のソケットでも HTTP/2 のストリームでも同じ API のまま成立する。
**Handler 側の拡張として、サーバーが提供する抽象の語彙で設計された
移譲だけがトランスポートの進化に耐える。** A.5 の 1〜3 が
「ソケット」ではなく「先読みバイトを内包した双方向ストリーム」を
渡すのはこのためである。

**移譲はストリーミング応答の双対であり、終端状態の追加にすぎない。**
HTTP/1.1 以降のサーバーの接続ループは、応答を書いたら閉じるのではなく
「本文の生産者が完了するまで接続を生かし、完了後に keep-alive で
次の要求へ戻る」状態機械である。ストリーミング Body は既に
writer・低速クライアント対策・切断時キャンセル・完了時後始末を備えた
長命タスクであり、移譲継続はそこに reader を一本加えた双対になる。
Warp の `responseRaw` の型
`(IO ByteString -> (ByteString -> IO ()) -> IO ())` が文字どおり
「reader + ストリーミング writer」であるのは偶然ではない。
ただし統一されるのは接続タスクの寿命管理であって HTTP 意味論ではない。
ストリーミング応答は完了後に次の要求へ戻れるが、移譲は戻る遷移を
持たない接続ループの終端状態である。状態機械としては「loop back
しない最終状態を一つ足す」変更であり、タイムアウト・キャンセル・
後始末の機構は既存ストリーミングのものを再利用できる。

本リポジトリの SSE 版が Lithe→Std ストリーミング Body アダプターのみで
成立した事実（第 2.3 節）は、`Std.Http.Server` がこの寿命管理機構を
既に持つことの傍証であり、移譲 API の実装コストが「ゼロから」ではなく
「終端状態の追加」である見通しを与える。
